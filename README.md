## Controls

Input is defined as semantic actions in [project.godot](project.godot). Gameplay consumes `attack`, `interact`, and the other named actions rather than physical keys or buttons. Radial selection is four rebindable actions (`radial_menu_up/down/left/right`) because it is a vector, while focused Godot Controls use the built-in `ui_up/down/left/right` actions automatically. Aim and attack are independent: `aim_up/down/left/right` only control pointing, and only inputs assigned to `attack` can shoot or slash. `InputManager` supplies movement, aim, radial-menu, and pointer intent; tracks the active input device; and applies radial right-stick hysteresis, so release noise cannot overwrite the last intentional aim direction. PlayStation L3/R3 conventionally means clicking a stick; the controls below use the left and right stick directions, not those clicks.

Current binding snapshot from `project.godot`: **25 actions, 51 event bindings** (21 keyboard/mouse and 30 controller assignments). The controller uses 11 physical control groups: left stick, right stick, D-pad, Cross, Circle, Square, Triangle, L2, R2, Options, and Touchpad. Counts below are event assignments, so one physical control reused by contextual actions is counted once in each action.

| Input actions | Purpose | Keyboard / mouse | PlayStation controller | Bindings |
| --- | --- | --- | --- | ---: |
| `up/down/left/right` | Move | Arrow keys + WASD | Left stick | 12 |
| `aim_up/down/left/right` | Aim / placement direction | Mouse handled separately | Right stick | 4 |
| `attack` | Shoot / slash | LMB | R2 | 2 |
| `interact` | Confirm menus / place turret | LMB | Cross | 2 |
| `open` | Open contextual menu | E | Square | 2 |
| `repair` | Repair turret | RMB | Cross | 2 |
| `cancel` | Close menu / cancel placement | Esc | Circle | 2 |
| `dash` | Charge / release dash | Space | L2 | 2 |
| `crunch_time` | Activate Crunch Time | E | Square | 2 |
| `skip_build_phase` | Start combat phase | B | Triangle | 2 |
| `pause` | Open / close pause menu | P | Options + Touchpad | 3 |
| `radial_menu_up/down/left/right` | Select a radial-shop sector | Mouse | D-pad + right stick | 8 |
| `ui_up/down/left/right` | Godot built-in UI navigation | Arrow keys | D-pad | 8 |

Intentional shared bindings: LMB is both `attack` and `interact`; Cross is `interact` and `repair`; E/Square are both `open` and `crunch_time`; D-pad directions are both `radial_menu_*` and `ui_*`; right-stick directions are both `aim_*` and `radial_menu_*`. Context owners consume overlapping actions before unrelated gameplay sees them.

The radial shop follows the active mouse or `radial_menu_*` direction; `interact` confirms its highlighted turret and `cancel` closes it. Focused Controls such as turret Upgrade/Sell use Godot's built-in `ui_*` focus navigation and retain their hold-to-confirm behavior through `interact`. Pause Resume and Game Over Restart also use `interact`. Open world menus join `open_input_blocking_menus`, preventing attacks from firing through them. `InputManager.device_changed` is the shared hook for future input-glyph switching.

To edit bindings in Godot, open **Project > Project Settings > Input Map**, search for an action such as `attack`, and expand it. Each action lists keyboard, mouse, and controller events together; use the plus button to add another event and the trash button beside an event to remove it. The project actions are `up/down/left/right`, `aim_up/down/left/right`, `attack`, `interact`, `open`, `repair`, `cancel`, `dash`, `crunch_time`, `pause`, `skip_build_phase`, and `radial_menu_up/down/left/right`, plus Godot's built-in `ui_up/down/left/right`. If Project Settings was already open while `project.godot` changed externally, close and reopen the dialog; restart the editor if it still shows stale actions.

Analog behavior that is not a physical binding lives in [input_manager.tscn](scenes/systems/input_manager.tscn). Open that scene from the FileSystem dock, select its `InputManager` root, and tune **Right Stick Aim > Aim Activation Deadzone**, **Aim Release Deadzone**, and **Pointing Turn Speed Degrees** in the Inspector. Release must be less than or equal to activation. Pointing turn speed is shared by the aim indicator and turret-placement ghosts, so both track the same interpolated direction without duplicating smoothing code. The Autoload tab only registers the scene; edit the scene itself rather than trying to inspect the running singleton there.

Remaining controller work is presentation/accessibility: live glyph swapping, runtime rebinding, persisted settings, and optional vibration. Manual controller passes should verify stick drift, diagonal movement, independent aim/attack, charged dash press/release, every shop/placement flow, turret upgrade/sell holds, pause/game-over focus, and seamless mouse/controller switching.

## Architecture

Four layers, signals flow **outward/upward**, direct calls flow **downward** to owned children only:

```text
UI          → reacts to signals, never mutates gameplay state directly
Systems     → WaveManager, SpawnManager, ShopManager, ScoreManager, GameOverManager, TimeScaleManager (scene-local); MenuManager, PostProcessingManager, and InputManager (autoloads)
World       → Player / enemies / turrets — orchestrator scripts composing components
Data        → Resource (.tres) subclasses — stats, never hold logic
```

Three infrastructure autoloads exist: `MenuManager` ([scripts/systems/menu_manager.gd](scripts/systems/menu_manager.gd)), `PostProcessingManager` ([scenes/systems/post_processing_manager.tscn](scenes/systems/post_processing_manager.tscn), script [scripts/systems/post_processing_manager.gd](scripts/systems/post_processing_manager.gd)), and `InputManager` ([scenes/systems/input_manager.tscn](scenes/systems/input_manager.tscn), script [scripts/systems/input_manager.gd](scripts/systems/input_manager.gd)). `InputManager` owns physical-device interpretation, active-device state, radial stick processing, and normalized movement/aim/menu intent; feature owners still decide whether an action is allowed and consume events at their existing gameplay or UI propagation layer. The post-processing and input-manager scenes expose their tuning in the Inspector. Gameplay systems remain scene-local under [scenes/game.tscn](scenes/game.tscn), because this is a single-session game — a global signal bus for everything would add indirection without benefit here.

`TimeScaleManager` ([scripts/systems/time_scale_manager.gd](scripts/systems/time_scale_manager.gd)) is the only writer of `Engine.time_scale`. Callers `request(source, scale)` / `release(source)` by `StringName`; the slowest active request wins, and `freeze(duration)` is a timed request at 0. This lets hitstop and dash slow-motion overlap without one resetting the other. It resets time to 1.0 when it leaves the tree.

`GameCamera` ([scripts/world/game_camera.gd](scripts/world/game_camera.gd), on the player's `Camera2D` in `game.tscn`) owns zoom the same way: `set_zoom_factor(source, factor, duration, ignore_time_scale)` tweens a named factor that multiplies onto the base zoom, so effects stack instead of overwriting each other. Crunch Time calls `set_crunch_time_active(active)`; the camera owns its `crunch_time_zoom_factor`, transition duration, and `&"crunch_time"` source key. Dash charge remains a separate `&"dash_charge"` factor requested by `Player`.

`PostProcessingManager` owns all full-screen world effects through one [post_processing.gdshader](shaders/post_processing.gdshader) compositor. Its CanvasLayer is layer 1 and game UI is explicitly layer 2, so post-processing never changes HUD, menus, labels, or indicators. Color/vignette callers use source-keyed `set_color_overlay(source, color, intensity, priority, fade_duration, pulse_speed)` / `clear_color_overlay(source)`: the highest priority wins and clearing it restores the next request. HUD forwards capacity to `update_capacity_effects()` and Crunch Time state to `set_crunch_time_overlay()`; `Player` fades the registered `&"dash_desaturation"` screen effect during dash charge. `reset()` runs when a fresh HUD starts so the persistent autoload cannot leak effects across scene reloads. Tuning lives in [post_processing_settings.tres](resources/post_processing_settings.tres). To add another scalar screen effect, add its uniform and fragment operation to the compositor, then call `register_screen_effect(id, uniform)` and use `set_screen_effect(id, amount, duration)`; keeping screen reads in one shader ensures effects compose in a defined order. The compositor ColorRect hides at zero strength, avoiding unnecessary screen copies.

Low capacity drives the independent registered `&"low_capacity_danger"` channel with five authoring controls in [post_processing_settings.tres](resources/post_processing_settings.tres). `danger_strength_curve` maps X = capacity fraction (0 empty, 1 full) to Y = final effect strength. Curve Y multiplies every authored maximum independently: effective glitch = `danger_glitch_intensity * Y`, aberration = `danger_chromatic_aberration * Y`, red tint = `danger_red_tint * Y`, and coverage = `danger_screen_coverage * Y`. Therefore Y = 1 displays exactly the four configured values. Coverage grows from the outer corners toward the center: the selected outer region receives the full effect, with a broad smooth elliptical feather at its inner boundary. Coverage 0 affects nothing and coverage 1 fills every pixel uniformly. Above 0.8 effective coverage, an internal full-screen base blends in progressively so near-death values keep the center strongly affected instead of reopening a pale hole. Red tint 1 produces a fully red luminance-preserving image wherever the mask is full. Desaturation, glitch timing/density/block proportions, maximum pixel offsets, and red tone are internally balanced ratios rather than exposed settings. The pattern re-rolls rather than travelling, so it feels alive without pulling focus. The legacy red capacity vignette has been removed; low capacity submits only this distortion channel. The optional high-capacity gold vignette remains separately controlled by `good_capacity_vignette_enabled`. Dash desaturation remains full-screen and combines with the danger effect; Crunch Time remains an independent color overlay.

Crunch Time combines a source-keyed gold vignette with the registered `&"crunch_time_screen"` channel. `PostProcessingSettings` owns all tuning: `crunch_overlay_color`/`intensity`, `crunch_overlay_pulse_speed`, and `crunch_overlay_pulse_min` control the pulsing vignette; `crunch_screen_tint_color`/`intensity` control the full-screen gold grade; `crunch_chromatic_aberration` controls a balanced maximum 4 px RGB split; and `crunch_bloom_intensity`/`crunch_bloom_radius` control an eight-tap bright-pass bloom. Bloom highlights receive the same gold grade as the world instead of being forced white. The bloom branch is skipped entirely while Crunch Time is inactive. Fade duration is `crunch_time_fade_duration`, and all effects stay below the UI CanvasLayer. The player-owned `CrunchShineParticles` node in [player.tscn](scenes/world/entities/player.tscn) emits small white atlas sparks radially while Crunch Time is active; amount, lifetime, velocity, damping, scale, and texture are scene-editable.

### Component ownership

Each entity (Player, Chaser, Stalker, Turret, …) is an **orchestrator**: it composes child component nodes and wires their signals together in `_ready()` → `_connect_signals()`. Components:

- own their own state (health, capacity, cooldowns, …)
- expose it through methods (`spend()`, `take_damage()`, `initialize()`) and signals (`health_changed`, `capacity_changed`)
- never reach into siblings or the parent scene

Fallible actions return `bool` (`try_shoot()`, `try_slash()`, `try_press()`) — the caller decides what happens on success (animation, sound, camera shake). The primary attack is automatic while its `attack` Input Map action is held: `Player._physics_process` calls `_process_held_primary_attack()`, which retries `try_shoot()` normally or `try_slash()` during Crunch Time; each weapon component owns its cooldown. Because LMB may be both `interact` and `attack`, `TurretPlacer` handles placement confirmation in `_input`, marks the event handled, and calls `InputManager.consume_attack_until_release()`; the latch also blocks continuous polling until the shared input returns neutral. Attacks are disabled for the duration of turret placement. Crunch Time buffs wrench damage, radius, arc, and cooldown without changing the wrench node's visual scale.

The player dash is charged: `DashComponent` runs `IDLE → HOLDING → CHARGING → DASHING → COOLDOWN`. `Player` calls `try_press()` on press and `release(direction)` on release or when `charge_maxed` fires. Releasing within `charge_delay` (HOLDING) is a plain `min_distance` dash with no slow-motion; past it the component enters CHARGING and emits `charge_started`. Both timers count real time (they divide out `Engine.time_scale`); `max_charge_time` is measured from the press. Distance is `lerp(min_distance, max_distance, charge_ratio)`; the dash starts at `dash_speed` and eases out, and `step_dash(delta)` integrates the exact displacement per physics step so the tuned distance is what the player travels. The component only emits `charge_started` / `charge_ended`; `Player` reacts by requesting/releasing `&"dash_charge"` on `TimeScaleManager` and playing `dash_charge` (slash frame 0, white `modulate` ramp, `WindupParticles`), speed-scaled so the ramp finishes at full charge; locomotion animations are skipped while charging. `dash_charge` and `dash` have priority 3, above `shoot`/`slash` at 2 and below `take_damage`/`die` at 4/5. `InputManager` interpolates one shared pointing direction at `pointing_turn_speed_degrees`; `AimIndicator` rotates a free-moving pivot to that direction while its child sprite counter-rotates to remain globally upright, and turret-placement ghosts consume the same direction, while gameplay aim itself remains immediate. While charging, `DashDirectionIndicator` points a sprite (default `assets/sprites/player/dash_direction.png`, drawn pointing right) in the dash direction. It extends [PixelRotatedSprite](scripts/shared/pixel_rotated_sprite.gd), the shared node for sprites that must rotate without deforming: it draws its texture through [shaders/pixel_rotate.gdshader](shaders/pixel_rotate.gdshader), which nearest-samples on a whole-pixel grid, and it owns the fade in/out. The dash indicator adds `top_level` plus whole-pixel snapping to the player so the grid never shifts. The off-screen turret arrows use the same node. While the player is invincible (dash held or dashing, or Crunch Time), `Player._sync_body_layer()` removes it from the `PlayerBody` physics layer each physics frame, so enemy hitboxes and projectiles pass through instead of triggering (e.g. Kamikazer explosions); while dashing it also drops `TurretBody` from its collision mask, so it dashes through turrets just like it already passes through enemies. All values come from the `PlayerStats` Dash group.

Enemies inherit the reusable [enemy_base.tscn](scenes/world/entities/enemy_base.tscn) template (script `EnemyBase`) for health, knockback, navigation, targeting, orb drops, contact hitbox, hit particles, death flash, damage/death handling, spawn intro state, conveyor velocity, and the shared `RESET`/`spawn_sleep`/`spawn_wake`/`take_damage`/`die` animations, which key only the empty `Visuals` node (see [Creating a new enemy](#creating-a-new-enemy)). Turrets inherit the reusable [turret_base.tscn](scenes/world/entities/turret_base.tscn) template for health, repair, upgrades, phase lifecycle, interaction UI, collision, particles, animation, and damage/death handling. `TurretBase` also initializes the common health bar and `TurretHUD`, whose upgrade panel owns the shared upgrade workflow. The base owns all common node names as direct children, including `Visuals`; derived scenes must put their body artwork below `Visuals` so inherited reset, repair, hit, and death animations can address the whole visual tree. Seeker and Shockwaver retain only their behavior-specific components and visuals. Stats resources are layered: shared fields at the top in a base class, type-specific fields in a subclass group below. `TurretStats` holds `max_health`, `damage`, `knockback`, `attack_range`, `attack_cooldown` (the same names `TurretUpgrade` uses), upgrades, selling, and repair; `SeekerStats`/`ShockwaverStats` add their own group. Enemies use `EnemyStats` (`max_health`, `damage`, `knockback`, `move_speed`, `targeting`, `orb_drop_amount`, `crunch_powerup_drop_chance`), extended by `ChaserStats`, `KamikazerStats`, and `RangedEnemyStats` (shared by ranged enemies; `StalkerStats` and `ShotgunnerStats` extend it).

Enemy drops are orbs. [orb.gd](scripts/world/pickups/orb.gd) (`Orb`, a `RigidBody2D`) owns the shared pickup lifecycle: `launch(impulse)` starts its freeze and `lifetime` timers, `_connect_phase_signals()` / `_is_clearing_phase_active()` decide which phase clears uncollected orbs (a drop landing after that phase already started, as the wave's last enemy does mid-death-animation, despawns straight away), and collection calls two hooks, `_try_collect(player)` and `_on_collected(player)`. Once the drop settles, the player magnetizes it: within `magnet_radius` the orb unfreezes and accelerates toward the player (`magnet_acceleration`, capped at `magnet_max_speed`) while the subclass's read-only `_can_attract(player)` hook is true (`player.can_pickup` for capacity orbs, `player.can_collect_crunch_powerup` for powerups), so an orb the player can't take stays put. A magnetized orb already overlapping the player is collected immediately. [orb_base.tscn](scenes/world/pickups/orb_base.tscn) is the art-free base: collision, detection, particles and the shared `RESET`/`pick_up`/`despawn` animations, which key the empty `Visuals` node's `scale` and `rotation` so any artwork put under it animates. Each pickup scene adds its own looping `idle` in a second `AnimationLibrary` on `AnimationHandler` (resolved by library search, so `play_animation("idle")` still works); `Orb` plays it on ready only when the scene provides one. Inherited scenes supply the look: [capacity_orb.tscn](scenes/world/pickups/capacity_orb.tscn) ([CapacityOrb](scripts/world/pickups/capacity_orb.gd)) restores capacity and survives the build phase so leftovers can still be collected, clearing when the next combat phase starts; [crunch_powerup.tscn](scenes/world/pickups/crunch_powerup.tscn) ([CrunchPowerup](scripts/world/pickups/crunch_powerup.gd)) carries the Crunch Time charge, clears as soon as combat ends, and reads [CrunchPowerupSettings](scripts/data/crunch_powerup_settings.gd) ([crunch_powerup_settings.tres](resources/player/crunch_powerup_settings.tres)) for its ground lifetime and trailing. `OrbDropComponent` on each enemy spawns `orb_drop_amount` capacity orbs from the `die` animation and rolls for a powerup. The roll is `crunch_powerup_drop_chance` plus `CrunchPowerupSettings.chance_per_turret` for every node in the `turrets` group, with that bonus capped at `max_turret_bonus`. Powerups never drop while Crunch Time is running; orbs are suppressed too unless the playtest toggle `CrunchPowerupSettings.drop_orbs_during_crunch_time` is on.

Crunch Time is charge-based. `CrunchTimeComponent` owns a single charge: `Player.try_collect_crunch_powerup()` calls `add_charge()`, which refuses while Crunch Time is running or a charge is already carried, so the powerup stays on the ground. The collected powerup trails the player until `charge_spent` (the `crunch_time` action calls `try_activate()`, which spends the charge) or `charge_lost` (the player is hit or dies, or `set_build_phase(true)` at round end). When Crunch Time ends, buffs, wrench mode, shine particles, and Crunch presentation stop immediately, while `Player` retains only invincibility for `PlayerStats.post_crunch_invincibility_duration` (default 0.5 s); this grace uses the same hit rejection and PlayerBody collision-layer path as normal Crunch invincibility. The HUD's ready label and `capacity_ready` animation follow the same signals. Capacity no longer gates Crunch Time and has no threshold.

Turret surface effects are part of the [turret_base.tscn](scenes/world/turrets/turret_base.tscn) contract: inherited `Visuals` owns one local-to-scene ShaderMaterial using [shaders/turret_surface.gdshader](shaders/turret_surface.gdshader), and rendered body/cannon sprites set `use_parent_material`; shadows do not. The shader composes [hit_flash.gdshaderinc](shaders/include/hit_flash.gdshaderinc), [gold_shine.gdshaderinc](shaders/include/gold_shine.gdshaderinc), and [damage.gdshaderinc](shaders/include/damage.gdshaderinc). Behavior animations key `Visuals:material:shader_parameter/flash_amount` directly, making white modulation previewable in AnimationPlayer. Persistent critical/max-level state remains code-owned, while hit feedback independently tweens `flash_amount` without interrupting behavior animations.

Critical turrets are flagged in two places. `TurretBase` listens to its own `HealthComponent.health_changed` and flips `_set_critical()` when health crosses `critical_health_ratio` (default 0.25), which recolours the sprite with a red tint pulsing between `tint_min` and `tint_max` while scorched pixels glitch in and out in place; selling clears it. On critical death, `_play_death_burnout()` enables the `die` animation's `death_burnout_progress` track, which fades damage red 1→0 while flashing white 0→1; key spacing in AnimationPlayer owns the duration. [CriticalTurretIndicators](scripts/ui/critical_turret_indicators.gd) (a full-rect `Control` in the `UI` layer of [game.tscn](scenes/game.tscn), above the HUD) caches the turret list when `ShopManager.turret_bought` fires and drops entries on `tree_exiting`, so it never scans the group per frame. Each frame it places a pulsing arrow `turret_offset` pixels from each critical turret, on the player's side of it and pointing back at the turret; the arrow only shows while the player is at least `min_player_distance` away, and fades out when the player closes in, on death, and on game over.

Turret repair is hold-to-repair: while the player is inside `InteractionZone` and holds the `repair` action (Left Shift; separate from `interact`, which is left click for turret placement), `TurretBase._physics_process` calls `RepairComponent.try_repair()` each frame (draining capacity at `repair_cost_per_second`, healing at `repair_health_per_second`) and plays a looping repair animation on the dedicated `RepairAnimationPlayer`, which pulses `Visuals:modulate` green and emits `RepairParticles`. Repair stops when the key is released, the player leaves, health is full, or capacity cannot cover the next tick; the repair player restores its own `RESET`. Turret combat remains active during repair: repair does not call `_on_combat_stopped()` and does not make `is_turret_active()` false, while the separate animation player lets the turret's attack animation and method tracks continue independently. Combat/build/game-over lifecycle still disables behavior normally.

Turret upgrades and selling use one upgrade panel per turret ([turret_hud.tscn](scenes/ui/turret_hud.tscn) → `TurretPanel`) with its own inline VBox of max health, damage, speed (`attack_cooldown`), and range rows. The shop's `TurretInfoPanel` has its own inline stats VBox. The `Upgrade` and `Sell` `HoldButton`s sit in a separate `Buttons` HBox below the turret that `TurretPanel` (a single `NinePatchRect` root that is also the outline) shows, hides, and scales in/out together with itself. Each button has an orb-price row directly beneath it; its `AnimationHandler` clips scale the hovered button up slightly and reveal the corresponding price row from underneath. Price label colors are set in the scene. Hovering Upgrade (mouse only; clicked buttons keep focus, so focus is not treated as hover) previews the next level by replacing changed values with their green new values. `TurretBase` owns the numbers: it tracks the current `TurretStatValues` (`get_stat_values()`), and `get_next_level_stats()` and `_on_upgraded()` both go through `_stats_after(upgrade)`, so the preview always matches the real upgrade. `TurretHUD` only moves its CanvasLayer origin onto the turret's screen position; panel and button placement is authored in `turret_hud.tscn` relative to that origin (top-left anchors), mirrored around the turret by `TurretPanel.flip_if_offscreen()` when the panel would leave the screen, with an editor-only `TurretPreview` Seeker sprite that is freed at runtime; its outlines use the turret's shop colors, which `ShopManager` hands over with `TurretBase.set_panel_colors()` on placement like the price and exclusion radius. Its `ToggleMenu` opens on proximity + `open` action, closes on leaving, toggle, cancel, or right click, and is disabled in combat phase. The turret's range indicator follows `TurretHUD.opened`/`closed`, so everything but the health bar is build-phase, press-to-open UI. When several proximity + button menus (turrets, shop station) have the player in range, `ToggleMenuComponent` opens only the nearest one, and only when none of them is already open. Level and health are also shown by the always-visible `HealthUIComponent` ([health_ui.tscn](scenes/ui/health_ui.tscn)): the level sits in the circle of `turret-health-ui.png` and the health fill in its bar. `HealthUIComponent` ([health_ui.gd](scripts/ui/health_ui.gd)) is a generic two-bar display: the exported `primary_bar` follows the assigned `HealthComponent`, the exported `secondary_bar` shows any 0-1 progress passed to `set_secondary_progress()`, and the optional `level_label` shows `set_level()`. Each bar's position, size and scale are authored on its ColorRect in the scene; the script only changes width (and, for right-to-left, the left edge). The script is a `@tool`: Inspector groups are `Nodes` (bars and label), `Primary Bar` (`primary_color`) and `Secondary Bar` (`secondary_color`, fill mode, direction, initial progress). Colors apply to the bars live in the editor; nothing else runs there, so bar widths are never altered in saved scenes. The `Secondary Bar` group selects `Fill` (grows with progress) or `Drain` (empties as progress rises), `Left To Right` or `Right To Left`, and the initial progress. Turrets connect their own `attack_cooldown_progress_changed` signal (emitted only when the value changes) to the secondary bar, so it remains a cooldown meter; other owners connect a different progress signal. `TurretHUD` forwards `upgrade_requested` / `sell_requested` to `TurretBase.try_upgrade()` / `sell()`. While Upgrade is held, `HoldButton` signals scale the base `upgrade_charge` animation to the hold duration; completed upgrades play `upgrade` (white `UpgradeParticles` burst). `TurretStats.upgrades` are ordered `TurretUpgrade` values multiplying the base stats (`-1` keeps the prior value; health/damage round to integers; cooldowns below `TurretBase.MIN_ATTACK_COOLDOWN` are clamped with a warning). Max level means all entries are applied; there is no wave gate. Max-health upgrades adjust current health by the same delta. When maxed and `stops_targeting_player_when_maxed` is true, the turret's `_stop_targeting_player()` hook runs (Seeker disables its `player` target group, Shockwaver stops triggering on the player); attacks can still damage the player. Selling refunds `sell_refund_ratio × total_invested`, capped at player max capacity, disables and fades the turret, frees the slot, and refunds player capacity.

Transient turret behavior animations key `Visuals:material:shader_parameter/flash_amount` directly; upgrade, upgrade charge, and Attractor pulse currently use this previewable contract. Death burnout timing is likewise authored in `die` through `death_burnout_progress`, while persistent critical/max-level state and concurrent hit feedback remain code-owned.

Repeated true signals do not retrigger until false rearms it, and cancellation/reset clears it. Landing directly executes the owned RadialWaveComponent, which owns damage detection and one-hit bookkeeping. After generic arrival, lifecycle code pins `Intro` in world space before any proprietary reveal and waits to restore gameplay until both clips are done. The fade-in is keyed in the boss's own intro: `bulwark/intro` sets it visible and fades modulate alpha 0 to 1 alongside the shield reveal.

### Adding A Boss

1. Create an inherited scene from [boss_enemy_base.tscn](scenes/world/enemies/boss_enemy_base.tscn), not directly from EnemyBase. Its root script must extend `BossEnemyBase`.
2. Add the boss's artwork children under the inherited `Visuals > DropRoot`; a Sprite2D named `Body` is a convenient convention, not a base-owned sprite. Assign its texture and enable `Use Parent Material` if it should share body/landing flashes. Scale/offset artwork children to suit the boss; leave DropRoot's resting position at (0, 0) and scale at (1, 1), since the shared timeline owns those properties. Ground shadows, UI, colliders, and gameplay components remain outside DropRoot.
3. The concrete boss's script extends `BossEnemyBase` and calls `_initialize_base(your_stats)` in `_ready()`, then configures contact damage, targeting, and its own gameplay components, just as Bulwark does. Assign body/contact shapes on the inherited CollisionShape2D slots; dimensions and stats belong to the concrete boss, not the generic base. Keep the inherited `Visuals` enemy-surface shader contract if replacing its material, so shared landing and hit flashes work. Idle/attack animations animate artwork children, not the intro-owned holder. No custom drop animation or spawn branch is needed.
4. If the boss has extra attack/shield/UI components, override `begin_spawn_intro()` / `_finish_spawn_intro()` to suspend and restore them, calling `super` just as Bulwark does. No override is needed for bosses with only the standard EnemyBase components.
	For a boss-specific reveal after arrival, add a non-looping `intro` to its existing AnimationHandler library, key only its proprietary artwork, and include those properties in that library's RESET. BossEnemyBase configures/plays it automatically and waits for it before restoring gameplay.
5. Create an `EnemySpawnEntry` pointing at the new scene and add it to `Systems > SpawnManager > Boss Entries` in [game.tscn](scenes/game.tscn). Set its introduction wave, enabled state, and scaling. The manager already selects entries and calls the inherited intro automatically: no new drop script, animation copy, spawn branch, or camera reference is needed.

Gameplay/visual feel is verified in-game; automated presentation tests are not required for routine timeline edits.

Targeting-only regression check: append `-- --targeting-only` to the Bulwark test command to verify player/turret preference without depending on sprite or balance tuning assertions.

Optional spawn-only regression check: append `-- --spawn-only` to check random placement, finite destination fallbacks, shared Emitter location picking, pending-wave gates, cancellation, and round-robin distribution independently of artwork assertions. In-game testing is the default; automated checks are used only when they answer a concrete behavioral question.

Protected hits route health loss through the owned HealthComponent but skip EnemyBase's body hit animation and particles. Only the shield sprite flashes white, using its independent scene-local enemy-surface ShaderMaterial and the shield's editable `Hit Flash Duration`; repeated hits restart its fade without sharing state between bosses. Exposed and bypass hits retain normal body hit feedback, and the shared death presentation is unchanged.

One node owns the whole shield: `Shield` ([directional_shield.gd](scripts/world/attacks/directional_shield.gd), `DirectionalShieldComponent`), an `AnimatableBody2D` on physics layer 8 (`EnemyShield`).

```text
Bulwark
	Visuals/DropRoot/ShieldSprite   <- shield art; stays in DropRoot so it falls with the body
	Shield                          <- facing, reduction, stress/break timer, tint, hit flash
		CollisionPolygon2D          <- projectile blocker
		ShieldHitbox                <- ram damage (HitboxComponent)
		ShieldWave                  <- top-level partial-ring RadialWaveComponent
```

The component rotates itself and its exported `sprite` to the facing angle, tints the sprite from stress/broken state (`Colors` group), and enables the collider and ram hitbox only while active (not broken, not in intro/death). The crescent polygon matches the sprite at its 2-pixel offset and sits outside animated `Visuals`, so visual scaling cannot scale physics. Projectile impacts call `Shield.was_hit()`, which emits `shield_hit`; Bulwark applies reduced damage/stress with zero knockback, including the armor-breaking hit. Exposed-side, broken-armor, and armor-bypassing hits retain incoming knockback. Player/turret projectile masks include EnemyShield; rings, Piercer, navigation, and body-only target acquisition do not. Projectiles immediately disable hit delivery after resolving one impact, preventing double damage from queued shield/body overlaps.

Shield attacks: `ShieldHitbox` (EnemyAttack layer, PlayerBody/TurretBody mask) uses `shield_damage`/`shield_knockback`, which outhit the standard body contact. While the shield is active and the target is within `shield_wave_trigger_range`, Bulwark's `shield_wave_cooldown` counts down, then it plays the locking `bulwark/shield_charge` clip: the boss stops, `ShieldSprite` pulls back and flashes white (material `flash_amount`), and a method key calls `launch_shield_wave()` → `Shield.launch_wave()`. `ShieldWave` is a `RadialWaveComponent` with `Arc Degrees` < 360, aimed through its `arc_direction` (the `pixel_ring` shader and the hit check both clip to the arc). Gameplay comes from the `Shield Attacks > Wave` stats in [bulwark_stats.tres](resources/enemies/bulwark/bulwark_stats.tres): damage, knockback, cooldown, trigger range, `shield_wave_range` (growth), `shield_wave_speed` (px/s; duration = range / speed), `shield_wave_width`, and `shield_wave_arc_degrees`. `Shield.configure()` pushes them into the wave, so only presentation (`Shockwave Color`/`Center Line Color`, `Pixel Size`, `Opacity Curve`) is edited on the node. Every RadialWaveComponent's `Opacity Curve` multiplies the color alpha with x measured in Expansion Durations: 0–1 is the growth, and a Max Domain above 1 keeps the settled ring at full size until x reaches it (e.g. domain 1.5 with a 1→1.5 fade = settle, then fade). Fades can also end before 1. Damage only happens while growing; the lingering visual runs independently of cooldown, and `shockwave_finished` fires when the visual ends (Mortar frees itself on it). `ShockwaveComponent` is a `@tool` script (runtime logic is skipped in the editor) whose exports are grouped into Shape, Timing, Hit, Trigger, Windup Indicator, and Look; each instance's `Stats Driven` flags hide the properties its owner overwrites from stats (Shockwaver: all but Arc, Mortar: all but Thickness and Arc, Bulwark shield wave: all, boss landing: none), and the Windup Indicator group hides when `Auto Trigger` is off. Breaking the armor or dying cancels a charge and restarts the cooldown.

Focused regression checks: run Godot with `--headless --path . --fixed-fps 60 res://tests/bulwark_tests.tscn --quit-after 1200`. The test scene covers armor/UI behavior, real bypass hit detection, boss intervals, balanced shuffled spawn distribution, entry/scaling, cancellation, scoring, and wave completion.

`SpawnManager` owns boss scheduling and its separate `Boss Entries` array, currently containing [bulwark_spawn.tres](resources/enemies/bulwark/bulwark_spawn.tres). `Boss Every Nth Round` selects one random enabled, introduced boss on each eligible wave (zero disables it; the current scene interval is 2). Its owned `BossLocationPicker` reuses [SafeSpotComponent](scripts/world/shared/safe_spot.gd), also used by Emitter. Bosses treat only turrets as threats: the player is excluded from both distance scoring and the boss picker's actor-clearance mask, so spawning on the player is allowed. Preferred samples are reachable and clear, maximizing distance from the nearest turret if the preferred distance is unavailable. Last-resort samples may overlap actors or be unreachable, but must pass wall-only clearance using the configured radius. The origin fallback also requires wall clearance. The scene defaults are 48 candidates, 180 pixels of preferred turret distance, and 32 pixels of clearance. If no wall-free destination exists among the samples or origin, the boss stays pending and retries every 0.25 seconds instead of spawning inside a wall. Placement is deferred out of physics processing and wall clearance is rechecked before spawning; generation guards cancel stale placements. The selected boss then runs the shared ground-warning/drop/landing intro described above before it can be targeted, collide, or attack.

SafeSpotComponent exposes one selection API: `pick_spot(navigation_map, navigation_layers, threats, from_position)`. It owns threat collection, navmesh sampling, reachability, and optional circular clearance checks. `Require Wall Clearance` makes walls a hard constraint for boss fallback selection; failure returns `Vector2.INF` only when no wall-free sample or origin was found. Emitter leaves that option disabled and retains its existing player/turret threats and finite-origin fallback policy. For performance the picker snapshots live threat positions once, scores squared distances, skips unnecessary expensive queries, and reuses collision query objects. Sampling is capped by `Candidates`; impossible boss placement is throttled rather than searched every physics tick.

[bulwark.tscn](scenes/world/enemies/bulwark.tscn) inherits EnemyBase and uses the dedicated Bulwark sprite, shared enemy targeting with a stronger player preference, existing navigation/contact damage, and a `DirectionalShieldComponent` that owns facing, frontal reduction, incoming-damage stress, delayed decay, and timed armor breaking. [bulwark_targeting.tres](resources/enemies/bulwark/bulwark_targeting.tres) allows turret targets but locks to the player within 120 pixels, switches away only when a turret is at least 100 pixels closer, and returns to the player when within 60 pixels of the turret's distance; same-group retarget margin remains 36 pixels. [bulwark_stats.tres](resources/enemies/bulwark/bulwark_stats.tres) owns gameplay tuning. The thin enemy root connects `Shield.stress_changed` to the secondary bar of the inherited boss health UI and overrides it to `Drain`, so the bar empties as stress builds. While broken, `stress_changed` counts the remaining break time down from 1, so the bar refills smoothly and is full exactly when the armor returns. `DirectionalShieldComponent` forces its sprite onto its own hit-flash material at ready (only death switches it to the body material). The bars span the whole frame with no level label; tune layout in [boss_health_ui.tscn](scenes/ui/boss_health_ui.tscn) without affecting turrets. Rings/explosions and Piercer call `was_hit_bypassing_armor()` when available; EnemyBase defaults that method to ordinary hit handling and Bulwark explicitly bypasses its armor, without changing the existing three-argument hit contract.

### Beamer

`BeamerStats.max_tracking_duration` limits accumulated target-tracking time per firing cycle (default 5 seconds; sweeping does not add heat). On overheating Beamer enters `COOLDOWN`, releases its lock, stops damage, fades the beam out, and returns to its idle animation. After `attack_cooldown` it resets heat and starts a fresh windup before firing again. Switching or briefly losing targets does not reset heat. The cooldown HUD and cooldown upgrades use the same timer.

[beamer.tscn](scenes/world/turrets/beamer.tscn) is registered through [beamer_shop_details.tres](resources/turrets/beamer/beamer_shop_details.tres). The beam behaviour lives directly in [beamer.gd](scripts/world/turrets/beamer.gd) (it is Beamer-only): continuous circular sweep, first-hit target lock, capped tracking speed, windup, overlap checks through the `Beam/BeamArea` Area2D, per-target damage intervals, and occlusion. `Beam` is a plain Node2D (z-index 8) grouping `BeamArea`, `SpeedParticles`, and the shared [LaserGraphics](scripts/world/attacks/laser_graphics.gd), which renders and fades the pixelated rounded beam. It returns to sweeping when its locked target dies, leaves range, is occluded, or moves beyond `lock_break_distance`. Base damage is 1 every 0.15 seconds; `hit_groups` (player, enemies) selects targets. Beam geometry checks world layer 1 so walls block damage. The turret and shop icon reuse a tinted Shockwaver atlas frame until dedicated Beamer art is available.

### Piercer

[piercer.tscn](scenes/world/turrets/piercer.tscn) reuses `TargetingComponent`, `AimingComponent`, and `LineOfSightComponent` with the Seeker targeting profile: enemies are primary and the player is fallback. ### Creating a new turret

`AimingComponent` owns both gameplay aiming and optional cannon presentation: it uses the same `aim_speed` for smooth Canon-pivot rotation, flips the Graphic vertically when the turret changes side, and flips Feet horizontally. `visual_turn_freedom_degrees` is the total visual arc around the outward direction (`180` = +/-90°, `90` = +/-45°); cannon sprites are authored facing right at zero rotation. Turrets with charge/telegraph attacks call `lock_aim()` when committing to a shot and `unlock_aim()` after firing or cancellation so gameplay and visual aim both hold steady.

1. Duplicate `turret_base.tscn` and save it as the new turret scene. Keep the common direct-child node names unchanged: `HealthComponent`, `HealthUIComponent`, `InteractionZone`, `TurretUpgradeComponent`, `RepairComponent`, `TurretExclusionZone`, `RangeIndicator`, `TurretHUD`, `AnimationHandler`, `RepairAnimationPlayer`, `Flash`, `HitParticles`, `UpgradeWindupParticles`, `RepairParticles`, and `Visuals`. A turret that needs an attack windup effect adds its own `WindupParticles` instance plus a `RESET` in its own animation library (Seeker, Shockwaver, Missiler).
2. Replace or add the turret artwork below `Visuals`. Put the main body at `Visuals/Sprite2D` or `Visuals/AnimatedSprite2D`; put a rotating cannon at `Visuals/Canon` and its artwork at `Visuals/Canon/Graphics` when the turret has one. Do not move `Visuals`, because inherited animations target that node.
3. Leave the base scene's `surface_shader` assigned. `TurretBase` installs separate materials on the body and cannon visuals at runtime. A missing shader is a configuration error and reports with `push_error`.
4. Add a turret script extending `TurretBase`. Export a stats resource that extends `TurretStats`, call `initialize_base(stats)` (it sets health, repair, upgrades, and the range indicator from `stats.attack_range`), initialize behavior components, and implement the turret's phase hooks (`_on_combat_started()` and `_on_combat_stopped()`) as needed.
5. Keep individual behavior in child components where practical. The turret script owns orchestration and wires those components together; components own their state and emit signals upward.
6. Override `set_damage(value)`, `set_attack_range(value)` and `set_attack_cooldown(value)` so an upgrade's absolute values reach the turret's damage source, attack range (update `range_indicator` too) and attack interval, and `_stop_targeting_player()` so the maxed turret stops selecting the player as a target. Override `get_attack_cooldown_progress()` to return normalized readiness (0 after firing, 1 when ready) for the shared cooldown fill. Author upgrade levels in the stats resource's `upgrades` array. Shared per-scene resources a turret mutates on upgrade (e.g. collision shapes) must be duplicated per instance.
7. Add behavior-specific animations to the inherited `AnimationHandler` library. Configure them in the script with `animation.configure_animation(name, priority, locks)` and use node paths relative to `AnimationHandler`. The shared `RepairAnimationPlayer` owns repair presentation independently so attacks can continue while repair is held. Keep `RESET` and `die` from the base library unless the turret has a deliberate replacement. For nodes introduced by an inherited turret scene, add a `RESET` animation to that scene's own animation library; `AnimationHandler` applies every library's `RESET` before playing a clip, so derived particle emitters can be reliably turned off without editing the base reset. Damage feedback is shader-driven; the base no longer carries unused idle or take-damage animation clips. If a turret script overrides `_physics_process`, it must call `super._physics_process(delta)` because `TurretBase` runs hold-to-repair there.
8. Add the new turret to its stats/resource files, shop entry, and `ShopManager` entries only after the standalone scene works. Placement uses the single [generic ghost scene](scenes/world/turrets/ghost_turret.tscn); do not create a turret-specific ghost. Set `TurretEntry.stats` to the turret's stats resource (the preview reads `attack_range`) and author its exclusion radius on `TurretEntry`. Set `Icon Source` to a [TurretIconTexture](scripts/shared/turret_icon_texture.gd), adding the turret sprite's `AtlasTexture` region(s) in draw order with pixel offsets matching the scene. `ShopManager` regenerates each entry's `ImageTexture` icon from that recipe when the game starts; no bake button or manual resource save is needed. Single-sprite turrets use one layer; body/cannon turrets compose feet/body first, then cannon layers.
9. Validate the scene with the editor command, run the scene standalone, and manually verify: health changes on damage, body/cannon flash white, repair and upgrade UI, phase transitions, behavior animation timing, death effects, and placement/shop flow.

### Creating a new enemy

Use [enemy_base.tscn](scenes/world/entities/enemy_base.tscn) as the starting template (Scene > New Inherited Scene). Chaser, Kamikazer, Stalker, Shotgunner and Emitter are built this way.

1. Keep the base direct-child node names: `CollisionShape2D`, `HitboxComponent` (+ its `CollisionShape2D`), `HealthComponent`, `KnockbackComponent`, `NavigationComponent`, `TargetingComponent`, `OrbDropComponent`, `AnimationHandler`, `Visuals`, `HitParticles`, `Flash`.
2. Assign a shape to both `CollisionShape2D` nodes; the base leaves them empty on purpose because every enemy has its own size.
3. Put all artwork (body sprite, shadow, lights, aim pivots) below `Visuals`. The base animations tint (spawn only), scale and hide `Visuals`, so everything under it follows spawn sleep/wake and death.
4. Set `use_parent_material = true` on the sprites that should flash white (the body, not the shadow). `Visuals` carries a local-to-scene `ShaderMaterial` with [enemy_surface.gdshader](shaders/enemy_surface.gdshader) (the shared [hit_flash.gdshaderinc](shaders/include/hit_flash.gdshaderinc)); `take_damage`, `die` and `RESET` key `Visuals:material:shader_parameter/flash_amount`, so flash timing is edited in the animations, not code.
5. Add a second library to `AnimationHandler` (e.g. `libraries/chaser`) with the enemy's `idle` and attack clips, plus its own `RESET` for tracks it animates. `AnimationHandler` applies the `RESET` of every library before each animation, so interrupted clips (e.g. windup particles) are restored.
6. Add a script extending `EnemyBase` with `@export var stats` (an `EnemyStats` subclass). Call `_initialize_base(stats)` (health, drops, and registration of the shared animations at priorities spawn 0, `take_damage` 2, `die` 3), then configure components and register the enemy's own animations (`idle` 0, attacks 1). Override `buff_damage()`, and `_before_handle_damage()` / `_before_handle_death()` to cancel attacks.
7. Override inherited node properties only where needed (e.g. Stalker sets `NavigationComponent.target_desired_distance`, Kamikazer sets the root `collision_mask`, each enemy sets its `HitParticles.process_material`).
8. Add an `EnemySpawnEntry` resource under `resources/enemies/<enemy>/` and list it in `Systems > SpawnManager > Enemy Entries` (or `Boss Entries`) in [game.tscn](scenes/game.tscn).

Ranged enemies share `RangedEnemyStats` (preferred distance, aim, shoot range, cooldown, projectile speed). Movement is a goal-provider component per enemy; the enemy script always walks to the returned goal through `NavigationComponent.get_safe_velocity()`:

- Shotgunner inlines a distance goal: walk directly at its target until it has line of sight and enters the preferred-distance band, then target the point `preferred_distance` away.
- `OrbitComponent` (Stalker): `APPROACH` walks to the nearest point on a circle of radius `preferred_distance` around the target (or to the target without line of sight). Within `preferred_distance_tolerance` of the circle and with line of sight it enters `ORBIT` in a random direction (50/50) and targets a point `orbit_lead_angle` degrees ahead on the circle, snapped onto the navmesh. It returns to `APPROACH` on lost line of sight, when it drifts beyond `tolerance + orbit_exit_margin`, or when stuck (moved less than `orbit_stuck_distance` within `orbit_stuck_time`); re-entry rolls a new direction, so a blocked stalker usually turns around. A target change resets it. The lead chord cuts slightly inside the circle, so a larger lead angle gives smoother but tighter orbits. Tuning lives in `StalkerStats` (Orbit group).

`ShootComponent` fires `projectile_count` projectiles evenly across `spread_angle` degrees (defaults 1 and 0).

The Shotgunner ([shotgunner.gd](scripts/world/enemies/shotgunner.gd), [shotgunner_stats.tres](resources/enemies/shotgunner/shotgunner_stats.tres)) walks directly toward its target until it has line of sight within the preferred-distance band, then maintains `preferred_distance`. Once in range, aimed and off cooldown it stands still with its aim locked and plays the one-shot `windup` animation (body shrinks, overlay builds toward yellow-white via the surface shader's `flash_color`/`flash_amount`), whose Call Method key calls `_execute_shot()` to fire `projectile_count` projectiles across `spread_angle`, then plays `shoot`. A successful shot applies `shot_recoil_force` through the shared KnockbackComponent opposite the aim direction; knockback remains authoritative while active, then navigation stays paused for the remainder of `confusion_movement_lock_duration` before the preselected relocation begins. The relocation samples reachable navmesh points and chooses the nearest candidate far enough away; `relocation_min_distance` is the minimum distance the Shotgunner itself travels, so destination selection adds the navigation arrival tolerance. The clip can be authored at any length: it is played at `length / windup_duration` speed so the stat sets the real duration. [ConfusedComponent](scripts/world/shared/confused.gd) extends `AnimatedSprite2D` and owns confusion duration, playback/visibility, an optional movement-lock window, and `confusion_ended`; enemy owners only start/stop it and decide how to honor `is_movement_locked()`. Shotgunner starts `Visuals/ConfusedSprite` for every attack cooldown and passes `confusion_movement_lock_duration` after either a successful shot or damage interrupting its windup. Its library `RESET` restores `flash_color` to white so later hit flashes stay white.

The Emitter ([emitter.gd](scripts/world/enemies/emitter.gd), [emitter_stats.tres](resources/enemies/emitter/emitter_stats.tres)) has two states. `RELOCATE` runs at its high `move_speed` via navigation to a spot chosen by `SafeSpotComponent`, which samples `spot_candidates` random navmesh points (`map_get_random_point`) and returns the first at least `spot_min_target_distance` from every node in its targeting profile's groups (player and turrets), else the safest sample. `EMIT` stands still, rotates `Visuals/EmitPivot` clockwise at `rotation_speed` and every `emit_interval` fires one projectile outward from `LeftMuzzle` and `RightMuzzle` (a two-armed spiral; the body sprite stays upright). A threat within `flee_radius` of the emitter while emitting, or of its destination while running, picks a new spot (re-picks are rate-limited to 0.5 s). A hit while actively emitting starts `hit_cooldown` and the shared `Visuals/ConfusedSprite` for the same duration; the timer runs every frame regardless of state, so time spent fleeing counts and it only waits out the remainder on arrival. Hits while running or recovering don't change behaviour. It deals contact damage through `HitboxComponent`; emission timing is owned by the script, so its `ShootComponent` cooldown is 0. It fires its own [emitter_projectile.tscn](scenes/world/entities/emitter_projectile.tscn).

### Creating a new projectile

Projectiles inherit [projectile_base.tscn](scenes/world/projectiles/projectile_base.tscn) (script [projectile.gd](scripts/world/attacks/projectile.gd)). The base owns `HitboxComponent` (+ empty `CollisionShape2D`), `AnimationHandler`, an empty `Visuals` node, `ExplosionVFX`, and the shared `RESET` / `hit` (explosion, hide `Visuals`, `queue_free`) / `despawn` (placeholder fade, ends with `queue_free`) animations keyed on `Visuals`.

1. Create an inherited scene; set the hitbox shape and collision layer/mask (and `no_damage_group` if needed).
2. Put the sprite and light under `Visuals`.
3. Optional: add a second `AnimationHandler` library with a looping `idle` (e.g. spin) and a `RESET` for its tracks; the base plays `idle` on ready if it exists.
4. Tick `despawn_on_build_phase` for enemy projectiles (Stalker, Shotgunner, Emitter); player and turret shots survive the phase change.

Lifetime comes from the shooter: each shooter's stats has `projectile_lifetime` (default 2 s; 0 or less = never) which its `ShootComponent` passes through `set_parameters()`. Lifetime expiry and the build phase call `despawn()`, which only plays `despawn`: the projectile keeps flying and can still hit, and a hit (`hit`, higher priority) overrides the fade.

### Asset references

Do not `preload()` textures, sprites or other art assets in scripts (e.g. as `@export` defaults). Declare the `@export var some_texture: Texture2D` without a default and assign it in the scene's Inspector. A preloaded path is invisible to the editor's dependency tracking, so moving or deleting the asset breaks script parsing instead of showing up as a missing reference in the scene. Report an unassigned export with `push_error` (see the fail-fast policy below).

Reusable particle scenes in [scenes/world/vfx/](scenes/world/vfx/) are `hit_particles.tscn`, `windup_particles.tscn`, `mist_particles.tscn` (Crunch shine), `speed_particles.tscn` (dash), `glitter_particles.tscn` (powerup), and `steam_particles.tscn` (repair). Only their six default process materials are saved in [materials/](materials/), named `hit`, `windup`, `mist`, `speed`, `glitter`, and `steam` with the `_particle_process_material.tres` suffix. Instance a core effect in its owner scene, keep the node name expected by animations/scripts, and override only the properties that differ. Store any unique material, including its nested gradients and curves, as subresources in the owner scene rather than saving a separate material file. Charge, glimmer, dash-charge windup, and turret upgrade are local variations.

`PixelCircle` ([pixel_circle.tscn](scenes/world/vfx/pixel_circle.tscn), [pixel_circle.gd](scripts/world/vfx/pixel_circle.gd)) is a white, texture-free, pixel-stepped circle/ellipse. Set `Shape`, local `Size`, and `Pixel Size` in the Inspector; use `modulate`/`self_modulate` for shadows and other tints. Standard enemy, turret, pickup, boss-intro, Mortar, shop-station, and conveyor shadows use this node instead of shadow art textures. Animated shadow sheets were replaced by AnimationPlayer tracks on `PixelCircle.size`.

Death and dash flashes are a hidden `Flash` `ColorRect` (40×40, centered) with a local-to-scene [pixel_ring.gdshader](shaders/pixel_ring.gdshader) material on the enemy base, turret base, and player. The owner's `die`/`dash` animation keys `Flash:visible` plus the material's `current_radius`, `ring_thickness`, and `shockwave_color` (thickness = 2 × radius draws a filled disc, then the ring thins and fades), and `RESET` hides it. `center_line_color` matches the ring color so the flash reads as one solid shape.

### Fail-fast guard policy

Do not use `is_inside_tree()` as a general error-suppression guard around normal calls. If a required node, resource, shader, animation, or component is missing, report it with `push_error` or an assertion so the configuration problem is visible immediately. Early returns are appropriate for expected gameplay state, such as cooldowns, disabled abilities, no target found, unaffordable actions, or a one-shot callback arriving after an object has already been invalidated.

The targeting system retains one explicit tree-membership check because it validates a cached target reference that can outlive or detach from the scene tree during enemy death. That is a stale-reference safety check, not a substitute for required initialization. The orb lifetime timer only checks `can_collect`; its lifecycle is controlled by the node and timer signal rather than silently ignoring a detached node.

### Node references

| Pattern | Use for |
|---|---|
| `$Child` | Own child in the same packed scene |
| `%UniqueName` | Scene-wide unique node, same scene owner (e.g. `%WaveManager` from anywhere in `game.tscn`) |
| `@export` | Cross-scene reference assigned in the inspector |
| `get_tree().get_first_node_in_group(...)` | Singleton-style managers reached from a different owner (e.g. turrets finding `player`) |
| `get_tree().get_nodes_in_group(...)` | Collections (`"enemies"`, `"turrets"`) |

### Stats resources

Balancing values live in one `Resource` subclass per entity type ([scripts/data/](scripts/data/)), instantiated as `.tres` variants ([resources/](resources/)). Entities read from `@export var stats: XStats` in `_initialize()` and push values into components — components never hold the resource directly. Variants are the same script with a different `.tres`, not a subclass.

Targeting uses one generic `TargetingComponent` ([targeting.gd](scripts/world/shared/targeting.gd)) configured by a `TargetingProfile` resource ([resources/enemies/enemy_targeting.tres](resources/enemies/enemy_targeting.tres), [resources/turrets/turret_targeting.tres](resources/turrets/turret_targeting.tres)) referenced from each stats resource (`ChaserStats.targeting`, `StalkerStats.targeting`, `KamikazerStats.targeting`, `SeekerStats.targeting`); Chaser and Stalker share `enemy_targeting.tres`, all Seekers share `turret_targeting.tres`, and the Kamikazer keeps a player-only `kamikazer_targeting.tres`. Resources are grouped by owner: `resources/player/`, `resources/enemies/<enemy>/` (stats, spawn details, own targeting), `resources/turrets/<turret>/` (stats, shop entry), shared profiles at the `enemies/` and `turrets/` roots, and `resources/waves/` (wave, spawn, conveyor settings). A profile has exactly two groups, `primary_group` and `secondary_group` (optional), and these rules run every call to `get_best_target(from, filter)`: (1) candidates must be alive, in an enabled group, within the component's per-instance `max_range`, and pass `filter` (Seeker: line of sight); an invalid current target is dropped with no hysteresis. (2) A primary target within `primary_lock_radius` always wins. (3) Otherwise the secondary target wins when `dist(primary) > dist(secondary) + switch_to_secondary_margin`, and keeps winning until `dist(primary) < dist(secondary) + return_to_primary_margin` (hysteresis band). (4) Within the chosen group the current target is kept unless a challenger satisfies `dist(challenger) + retarget_margin < dist(current)`. `target_changed(new, old)` fires on every switch (Chaser resets its attack latch). Chaser movement: each chaser walks (navigation + avoidance) toward its target plus a personal random `flank_distance` offset that fades from full beyond `flank_full_distance` to zero inside `flank_zero_distance`, so groups fan out and arrive from different sides but always converge on the target itself; the flank is dropped (one-way, reset on target change) once reached. Within 32 px it steers straight at the target. Enemies ride conveyors as passengers (`EnemyBase._add_conveyor_velocity()`): on a belt they stop walking and are carried, so they never fight a belt that is faster than they walk. The floor `TileMapLayer` uses `NavigationMapLayer` ([scripts/world/navigation_map_layer.gd](scripts/world/navigation_map_layer.gd)), which disables per-tile navigation and bakes one navigation mesh at runtime from cells whose tile has a navigation polygon, minus colliders of nodes in the `navigation_obstacles` group (the tilemap itself and the shop station) and conveyor belts (group `conveyor_belts`), eroded by `agent_radius` (14 px, plus `conveyor_clearance` 10 px around belts) so paths keep enemy bodies off walls, corners, and belt edges. All enemies (Chaser, Stalker, Kamikazer) share the same navigation rules: this baked mesh, shortest-path (corridor funnel) routing, conveyor passenger mode, and NavigationAgent2D avoidance with radius 14, neighbor_distance 80, max_neighbors 10, time_horizon_agents 1.5 for spacing (Kamikazer switches avoidance off while charging); the final straight-line approach also goes through avoidance via `NavigationComponent.get_safe_direct_velocity()`. Off-mesh flank points are snapped onto the walkable area rather than dropped. Turrets are not baked in (placed at runtime). Enemies use player-primary / turrets-secondary with a lock radius so the player can pull aggro off turrets; Seekers use enemies-primary / player-secondary and disable the `player` group when maxed. Each `debug_*` flag on a profile draws one ring on the ground for every entity using it (`TargetingDebugDraw`, toggleable live): white = max range, yellow = lock radius, blue = distance to nearest primary, orange = distance to nearest secondary, red = switch ring (primary leaving it -> secondary chosen), purple = return ring (primary entering it -> back to primary), green = retarget ring, plus a line to the current target. The switch/return rings are never drawn smaller than the lock radius, since the lock overrides them.

### Known deliberate deviations from a "pure" component model

A few places intentionally cross the strict ownership boundary because the added indirection isn't worth it for a single-scene game:

- Turret repair drains player capacity directly (`repair.capacity_drained.connect(player.capacity.spend)`) rather than going through an event/coordinator layer.
- Factories (`ShootComponent`, `TurretPlacer`) call `get_tree().current_scene.add_child(...)` directly. Enemy spawning is centralized in `SpawnManager` with an injected destination container; another coordinator for the remaining projectile/placement factories adds no value in this single-scene game.
- `boss_enemy_base.tscn` duplicates the `enemy_base.tscn` node layout instead of inheriting it, so bosses own and can edit every animation (including `RESET`). Keep EnemyBase node names in sync in both scenes when changing the `EnemyBase` script's node contract.
- `OrbDropComponent.drop()` looks up the player via `get_tree().get_first_node_in_group("player")` and reads `player.crunch_time.is_crunch_time_active()` directly to skip orb and powerup drops during crunch time, instead of the player broadcasting a "no drops" event enemies subscribe to.
- `PostProcessingManager` is an autoload with a direct global call API because color overlays and full-screen effects are cross-cutting presentation used by unrelated gameplay/UI owners; a scene-local bus plus coordinator would add indirection while still requiring one persistent compositor.
- `TurretBase` reads the `repair` input directly (`Input.is_action_pressed`) instead of the player routing it to the nearest turret; with at most a handful of turrets, a player-side turret selection layer would add more indirection than value.
- `TurretBase` reads `player.capacity.can_afford()` to decide whether the upgrade button is enabled. Spending and refunds still flow as signals (`TurretBase.upgrade_purchased` / `sold` → `ShopManager.turret_upgraded` / `turret_sold` → `Player`); only the read-only affordability check crosses the boundary, because a signal round-trip for a per-frame button state adds no value.

These are acceptable trade-offs, not bugs — revisit only if the game grows multiple scenes or needs pooling/threading.

### Enemy spawn intro

`SpawnPoint` markers sit outside the playable area and own only `spawn_intro_direction`, `spawn_intro_distance`, and their conveyor settings. `SpawnManager` instantiates and assigns each enemy, then calls the selected point's `send_in(enemy)`. The point asks the assigned `EnemyBase` to perform its existing non-colliding, invulnerable, AI-disabled entrance tween and sleep/wake visuals. Intro duration is distance divided by `ConveyorSettings.enemy_movement_speed`. On arrival, EnemyBase restores collision, contact damage, and AI. Points contain no enemy configuration, queues, scaling, timing, boss selection, or wave subscriptions.

Conveyor belts are inline `Area2D` components in the level scene, not standalone scenes. Each uses [scripts/world/spawners/conveyor_belt.gd](scripts/world/spawners/conveyor_belt.gd), detects PlayerBody and EnemyBody layers, and owns a child `CollisionShape2D` whose dimensions are currently authored in the level scene. Both the belt and spawner reference [resources/waves/conveyor_settings.tres](resources/waves/conveyor_settings.tres), the single source of truth for `enemy_movement_speed` and `player_movement_speed`. The belt talks to bodies only through `set_conveyor_velocity()` / `clear_conveyor_velocity()`; while overlapping, the matching conveyor velocity is added to normal player/enemy movement so they can steer off the belt. The spawn tween remains responsible for crossing the outer wall while collision is disabled.

Continuous environmental motion composes through `ExternalVelocityComponent` ([external_velocity.gd](scripts/world/shared/external_velocity.gd)), present on Player and EnemyBase. Sources set or clear a velocity by integer source ID through each body's public `set_external_velocity()` / `clear_external_velocity()` contract; the component sums independent sources without knowing their owners. Player applies the sum only during normal movement, so dash and knockback remain authoritative. Enemies apply it after normal navigation, except knockback remains authoritative and conveyor passenger mode still replaces walking before external velocity is added. This contract is used by Attractor and is the extension point for future wind or current fields.

### Wave System

Build-phase duration is configured in [resources/wave_settings.tres](resources/waves/wave_settings.tres) as `build_phase_duration`.

The phase lever ([lever.tscn](scenes/world/environment/lever.tscn), [lever.gd](scripts/world/environment/lever.gd)) listens directly to `WaveManager` phase signals. Build phase sets its editable `build_phase_color` (green) and plays low-priority `swing_left`; combat phase sets `combat_phase_color` (red) and plays locking, higher-priority `swing_right`. During build phase, its Area2D opts into the generic player-projectile `receive_player_projectile_hit()` contract; an accepted hit calls `WaveManager.skip_build_phase()`, resolves that projectile, and ignores duplicate requests until the next build phase. In combat the contract returns false, so player projectiles pass through.

`WaveManager` and [SpawnManager](scripts/systems/spawn_manager.gd) are siblings under `Game > Systems`. Scene connections forward combat start to `start_wave()`, build start to `cancel_wave()`, and `wave_cleared(wave_index)` back to WaveManager. Neither manager directly controls its sibling. ScoreManager receives the single `enemy_defeated` event instead of subscribing separately to enemy death signals.

Configure `Systems > SpawnManager` in [game.tscn](scenes/game.tscn): `Enemy Entries`, `Boss Entries`, `Spawn Points`, `Time Between Spawns`, `Damage Growth`, and `Boss Every Nth Round`. Existing `EnemySpawnEntry` resources own enabled state, introduction wave, wave-wide base amount, growth, and health scaling. The manager builds one shuffled queue and shuffles point order every round, assigning queue entries round-robin; point totals differ by at most one while enemy types and the extra-enemy recipient vary randomly. Adding a point redistributes the configured total instead of multiplying it.

Migration from two autonomous spawners sets normal entries' base amounts to 2 and the global interval to 0.75 seconds, preserving initial totals and the previous average rate of two enemies per 1.5 seconds. Later growth rounds once per global total, rather than independently per point. SpawnManager owns instantiation into its injected `World` container, health/damage scaling, live-enemy tracking, pending queue state, and generation-based cancellation. It signals completion only when the queue is exhausted and no tracked enemies remain; stale deaths and cancelled schedules cannot finish another wave. Pickups retain their existing phase lifecycle.

### Type-safety standard

This project uses strict GDScript typing for signal callbacks and loops. Any anonymous function passed to `connect()` must either declare its parameter type(s) or include an explicit `-> void` return type. Any `for` loop variable that is not inference-safe should be explicitly typed, e.g. `for rider: Node in _riders.values():` and `for factor: float in _factors.values():`. If a value can be ambiguous, declare its type explicitly (`var intro_speed: float = ...`). This is not style-only; it keeps Godot diagnostics clean and prevents silent type drift.

### Crunch-time visual effects system

Crunch-time presentation has explicit owners. `PostProcessingManager` and [post_processing_settings.tres](resources/post_processing_settings.tres) own every full-screen effect; `GameCamera` owns zoom factor and transition timing; and the HUD scene owns the ready label text/layout plus its editable AnimationPlayer clips. `CrunchTimeComponent` owns only charge, fixed-duration lifecycle, and gameplay buff values from [player_stats.tres](resources/player/player_stats.tres); it tells the injected camera when the state changes and emits signals that HUD forwards to post-processing. The HUD AnimationPlayer owns the capacity bar's `capacity_ready`, `capacity_active`, and `capacity_change` motion; the ready label's size pulse is a track inside `capacity_ready`. These clips use integer-pixel vertical movement and no scale/rotation on the pixel-art bar, so timing and keyframes can be adjusted directly in the scene editor without subpixel distortion.

### Primary Attack Routing

The player owns its damage self-knockback through `PlayerStats.damage_knockback_force` (default 200); accepted nonfatal hits use the larger of that setting and the attacker's force, so ordinary hits feel consistent while heavy attacks (Bulwark shield, Kamikazer) push harder. Enemy self-knockback/recoil behavior remains enemy-owned, and other damage recipients retain incoming attack forces. Shared projectiles pass their travel direction to the owned hitbox and update it on deflection, so projectile knockback follows travel even when projectile and target centers coincide. `HitboxComponent.knockback_direction` defaults to zero to retain contact-hit direction from hitbox position. Player invincibility and the existing stronger death knockback still apply.

Shared hit rules: every non-hitbox attack (`RadialWaveComponent`, Piercer, Beamer, Linker) uses the static `HitboxComponent.can_hit(body, groups)` (takes hits, alive, in one of the groups) and `HitboxComponent.apply_hit(body, damage, knockback, origin, bypass_armor)` instead of its own copies. Each owner exposes its targets as an exported `target_groups`/`hit_groups` array; radial waves and Piercer bypass armor. Knockback is passed to every target; recipients decide how to use it.

Component policy: reusable behavior lives in shared components (`RadialWaveComponent`, `RadialFieldComponent`, `LaserGraphics`, `LineOfSightComponent`, `TargetingComponent`, ...). Behavior used by only one entity (Piercer's wall-clipped shot, Beamer's sweep/overheat, Linker's chain) lives in that entity's own script, grouped under plain Node2D pivots in its scene rather than in one-off component scripts.

`Player` routes the primary attack action to `ShootComponent` normally and `MeleeWeapon` during Crunch Time. `MeleeWeapon` handles enemy bodies through `HitboxComponent` and projectile areas through the generic `receive_wrench_hit()` contract. Turrets do not implement that contract; they are repaired only by hold-to-repair.

### Turret shop

The shop station's `ToggleMenuComponent` opens [shop_panel.tscn](scenes/ui/shop_panel.tscn) (`ShopPanel`) through `ShopManager`, which passes the `TurretEntry` list, `player.can_afford`, and whether `max_turrets` is reached. `ShopPanel` is presentation only: it instances one [turret_card.tscn](scenes/ui/turret_card.tscn) (`TurretCard`, icon only) per entry, spread evenly on a circle of `radius` around the center [turret_info_panel.tscn](scenes/ui/turret_info_panel.tscn) (`TurretInfoPanel`: name, price, then icon + value rows for health, damage, and speed = `attack_cooldown`; a label appears when the turret limit is reached). The direction from the screen center to the mouse picks the highlighted card by sector, starting at `start_angle_degrees` and going clockwise; inside `dead_zone_radius` the last highlight is kept. The full-screen root consumes mouse clicks while open so the player never shoots through it (it sets every Control under `Content`, including spawned cards, to `MOUSE_FILTER_IGNORE`, so restyled layouts can't swallow clicks): left click emits `turret_selected(entry)` (unaffordable or limit-blocked cards play `reject` instead), right click emits `close_requested`; `ShopManager` starts placement or closes the menu. E, Esc, and walking away still close it, and click-away closing is off. All motion lives in `AnimationHandler` clips: `appear`/`disappear` on the shop, `highlight`/`settle`/`reject` on each card (keying `TurretCard.pop_amount`, which slides the card's `%Edge` node `pop_distance` px outward, plus `Control/Edge:modulate` for brightness; they have no `RESET` and rely on the player's default blend time so interrupted transitions stay smooth), and `refresh` on the info panel. Each `TurretEntry` has `outline_start_color`/`outline_end_color` (Shop Colors group); each `TurretCard` colors its own `%Outline` (local-to-scene material) with them in `populate()`, and when the highlight changes, `refresh` keys `TurretInfoPanel.outline_fill` 0→1, which blends the `start_color`/`end_color` of `PanelOutline` and `StatsOutline` from the colors currently shown to the new turret's. [pixelated_gradient_pulsing.gdshader](shaders/pixelated_gradient_pulsing.gdshader) itself only exposes `start_color`, `end_color`, `pulse_speed`, `pulse_width`, and `gradient_steps`. The panel duplicates the outline material because `circulating_gradient_blue.tres` is shared with the HUD. Stat icons are placeholders assigned in the info panel scene. The selection works from a direction vector so a gamepad stick can drive it later.

### Shockwaver Prototype

[scenes/world/turrets/shockwaver.tscn](scenes/world/turrets/shockwaver.tscn) is registered through [resources/turrets/shockwaver/shockwaver_shop_details.tres](resources/turrets/shockwaver/shockwaver_shop_details.tres), alongside Seeker. `RadialWaveComponent` owns contact detection, windup, expanding annulus rendering, one-hit-per-target tracking, multi-target damage, and cooldown. The blast itself is keyed in the `shock` animation, so `Shockwaver` calls `cancel_windup()` whenever `play_animation("shock")` is refused by a higher-priority lock (upgrade, repair); the component drops back to `READY` and retries next frame instead of stranding in `WINDUP`. The expanding ring uses [shaders/pixel_ring.gdshader](shaders/pixel_ring.gdshader), which generates a symmetric hard-edged ring from quantized fragment coordinates on a dedicated square canvas. Tune `RadialWaveComponent.shockwave_color`, `RadialWaveComponent.pixel_size`, `RadialWaveComponent.center_line_color`, and `RadialWaveComponent.center_line_thickness` in the scene Inspector; these control the ring color, pixel block size, centerline color, and centerline width in pixel-grid cells. The default centerline thickness is one pixel. Knockback is authored as `TurretStats.knockback` on the Shockwaver stats and is passed to every target hit (the player still uses at least its own damage knockback). The broad-phase `Area2D` detects player/enemy bodies; radial swept-ring math determines when the moving doughnut reaches each target without scaling collision shapes. `TurretEntry.stats` (typed `TurretStats`) supplies the placement preview range via the shared `attack_range`, and `TurretEntry` owns the exclusion radius; `ShopManager` applies `exclusion_radius` to the placed turret via `TurretBase.set_exclusion_radius()` (turrets not placed through the shop keep the `TurretExclusionZone` default). The Shockwaver uses a single `ShockwaverStats.max_range` as both trigger distance and blast radius.

### Attractor Prototype

[attractor.tscn](scenes/world/turrets/attractor.tscn) inherits TurretBase and is registered through [attractor_shop_details.tres](resources/turrets/attractor/attractor_shop_details.tres). The shared `RadialFieldComponent` ([radial_field.gd](scripts/world/attacks/radial_field.gd)) owns `READY → WINDUP → ACTIVE → COOLDOWN`, target overlap, radial force falloff, source cleanup, optional projectile deflection, and field drawing. Attractor configures its inward mode without projectile interaction; [attractor_stats.tres](resources/turrets/attractor/attractor_stats.tres) retains its pull tuning.

### Repulsor

[repulsor.tscn](scenes/world/turrets/repulsor.tscn) uses the same `RadialFieldComponent` in outward mode. While active, it pushes enemies and the player through external velocity and deflects each overlapping shared `Projectile` once per pulse, preserving speed and collision behavior. Projectiles expose `deflect_away_from()` and join the `projectiles` group; MortarStrike remains unaffected. ### Linker

Cooldown starts only after firing at at least one eligible target. A charge that expires with no damageable linked targets cancels without cooldown, clears its visuals, and stops the charge animation so the turret can acquire again.

[linker_laser.tscn](scenes/world/turrets/linker_laser.tscn) supplies the shared `LaserGraphics` child under the plain `Chain` Node2D (z-index 8) in [linker.tscn](scenes/world/turrets/linker.tscn). Select `Chain > LaserGraphics` there to tune link width, center thickness, colors, pixel shader, telegraph opacity/fade-in, firing fade-in, fade-out delay, and fade-out duration in the Inspector. The child is a hidden runtime template; its `create_instance()` method copies the authored settings into each live chain segment (added under `Chain`) without duplicating runtime visuals. Linker owns chain behavior and gameplay charge/fire timing, not visual lifetime.

The shared `LaserGraphics` ([laser_graphics.gd](scripts/world/attacks/laser_graphics.gd)) owns the complete laser presentation lifecycle: `show_segment(start, end)`, `show_telegraph()`, `show_fire()` (brighten, wait `fade_out_delay` seconds from firing, then fade out), and `cancel_telegraph()`. Its exported parameters have Inspector documentation. Piercer uses the same API through its root-level `LaserGraphics` in [piercer.tscn](scenes/world/turrets/piercer.tscn). Telegraph fade duration is independent of gameplay charge duration. Continuous Beamer visuals retain `fade_to()` and use the same graphics-owned fade duration.

Telegraphing draws only one solid line using `telegraph_width` and `telegraph_color`; firing switches to the full capsule with `laser_width`, center thickness, and center/edge colors. Both modes share beam length, aiming, and pixel rotation, so moving chain links retain their current endpoints.

Linker's last-target range circle fades in using the laser child's `telegraph_fade_duration`, matching each new telegraph line. Extending the chain restarts the circle fade at the new endpoint; following an existing endpoint does not restart it. Other `RangeIndicator` callers remain instant unless they pass a fade duration to `show_indicator()`.

[linker.tscn](scenes/world/turrets/linker.tscn)'s Linker-only chain logic lives directly in [linker.gd](scripts/world/turrets/linker.gd). It builds the closest chain of bodies in `hit_groups` (enemies, player), requiring each unlinked target to be within `attack_range` of the previous target and visible through `LineOfSightComponent`. There is no chain cap. Every charging tick, including the firing tick, it checks live hop distances starting at the turret. The first out-of-range or ineligible target and all downstream targets detach, and their laser segments are removed. The retained endpoint can immediately append nearby targets using the existing range/LOS rules; if nothing remains, acquisition restarts from the turret. Breaking or extending links does not restart the charge timer. Shared `LaserGraphics` segments track the turret and linked targets; firing damages only surviving targets still linked and starts the normal cooldown. One turret-owned `RangeIndicator` follows only the last target during charging to show the next-hop radius, disappearing on firing or cancellation. At max level it no longer selects the player. Stats and upgrades are in [linker_stats.tres](resources/turrets/linker/linker_stats.tres); body, placement ghost, and shop use `linker.png`.

### Missiler Prototype

[missiler.tscn](scenes/world/turrets/missiler.tscn) is registered through [missiler_shop_details.tres](resources/turrets/missiler/missiler_shop_details.tres). `Missiler` reuses `TargetingComponent`, `AimingComponent`, `TurretBase` lifecycle/upgrade/repair/HUD behavior, and `RadialWaveComponent` in manual-trigger mode. It locks a target position outside `minimum_range`, shows a fixed procedural impact marker, launches an independent [mortar_strike.tscn](scenes/world/turrets/mortar_strike.tscn) after the authored `launch` charge animation, and lets the strike manually execute the existing expanding ring. The strike owns its locked destination, flight arc, impact timing, and cleanup, so it survives the turret being interrupted after launch. Its derived animation library defines a `RESET` clip that turns off `WindupParticles` and muzzle `ShootParticles`; this keeps those scene-specific nodes resettable without modifying the inherited base library. `MissilerStats` owns targeting/range, charge/flight timing, arc height, blast radius, damage, knockback, cooldown, and upgrades; `mortar_strike.tscn` owns ring thickness, colors, pixel size, fade, and other radial-wave presentation. Placeholder art reuses the Shockwaver atlas; the turret's `TurretEntry.Icon Source` provides the runtime shop icon, and the generic ghost displays that generated icon.

## Testing

No automated test framework is installed yet. Godot's community standard is **GUT (Godot Unit Test)**, run headlessly.

Worth unit-testing (pure logic, no input/physics/timing dependency):
`CapacityComponent`, `HealthComponent`, `RepairComponent`, `TargetingComponent`, queue/distribution/scaling and cancellation in `SpawnManager`.

Not worth automating: movement feel, animation timing, camera shake, turret-placement UX — these need manual play-testing.
